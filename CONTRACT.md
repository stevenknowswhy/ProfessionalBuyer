# Contract between frontend and backend

The frontend agent ([PLAN-frontend.md](PLAN-frontend.md)) and the backend agent ([PLAN-backend.md](PLAN-backend.md)) never talk to each other directly. They meet at this contract.

- **Schemas and types:** [`contract/src/index.ts`](contract/src/index.ts) (Zod). Both sides import `@buyer/contract`.
- **Landed-cost math:** [`contract/src/landed-cost.ts`](contract/src/landed-cost.ts). The only place these formulas exist. The backend calls them; the UI never recomputes a dollar figure, it displays what it is sent.
- **Sample data:** [`contract/fixtures/*.sample.json`](contract/fixtures). Generated by `pnpm --filter @buyer/contract fixtures`, validated by `pnpm contract:check`. The frontend builds against these; the backend serves them from day one as stubs.

Money is integer cents. Timestamps are ISO-8601 UTC. IDs are opaque strings.

## Runtime

| Thing | Value |
|---|---|
| Backend base URL | `http://localhost:4111` (Mastra server). Env on the web side: `NEXT_PUBLIC_API_BASE` |
| Web app | `http://localhost:3000` |
| CORS | Backend allows `http://localhost:3000` (and the deployed web origin if any) |
| Auth | None. Single demo household. Do not add login |

## Chat tool results

The agent calls tools; each tool result is rendered by the frontend as a designed card, keyed by tool name. Schemas are in `ToolResults`.

| Tool name | Result | Card |
|---|---|---|
| `showSavings` | `SavingsRun` | The Number, with the "How this was computed" drawer |
| `showOffers` | `ItemSavings` | Price comparison: channels, delivered cost, unit cost, excluded offers with reasons |
| `proposePurchase` | `Approval` (status `pending`) | Approval card: merchant, amount, cap, formula, Approve and Decline |
| `showLiveView` | `{kernelSessionId, liveViewUrl, caption}` | Embedded Kernel live browser |

Text never carries the numbers alone. If a figure is mentioned in prose, it is also in a tool result.

## Approval flow (both sides rely on this)

1. Agent calls `proposePurchase`. Backend writes an `Approval` row (`pending`) and returns it as the tool result.
2. The card renders. **The card always calls `POST /api/approvals/:id/approve` or `/decline`.** It does not depend on how the backend resumes the agent.
3. Backend `approve` checks: amount is at most `SPEND_CAP_USD`, merchant is on the allowlist, and `offerHash` matches the offer re-read now. Failure sets `blocked` with a plain-English `blockedReason`.
4. Backend runs the checkout (Kernel). The approval moves `executing` then `completed`, with `checkout.liveViewUrl` filled as soon as the browser exists. The UI polls `GET /api/approvals` every second while `executing`, and the trace stream shows the steps.
5. `mode: "review"` stops at the order-review page (`stoppedAt: "review-page"`). `mode: "place"` places the order (`stoppedAt: "placed"`).

How the backend resumes the Mastra agent (native `requireApproval` and `approveToolCall`, or a plain function call) is a backend detail that never changes this contract.

## Labeling rules the frontend enforces

- `provenance: "sample"` shows a visible "Sample data" badge. `"replayed"` shows "Replayed". Only `"live"` shows no badge.
- `Health.services[].usingFallback` shows the fallback label next to that sponsor.
- `Household.isDemoHousehold` shows "Demo household".
- `SavingsRun.inputs.salesTaxIncluded` is always `false` and `dutyIsEstimate` always `true`; the UI states both in the drawer.
- `ItemSavings.history.enough === false` shows the reason and excludes the item from the total.

## Changing the contract

The contract is what lets two agents work in parallel, so changes must be cheap and safe.

1. **Additive changes are allowed any time** by either agent: a new optional field, a new endpoint, a new sponsor chip. Make the change in `contract/src/index.ts`, regenerate fixtures, run `pnpm contract:check`, and push it in a small PR titled `contract: ...`. The other agent pulls `main` when it lands.
2. **Breaking changes** (rename, remove, retype, make a field required) require the human's OK in the PR. Avoid them. After 2:30 PM do not make any.
3. Never fork the contract by redefining types locally. If a type is missing, add it here first.
4. Never hand-edit `fixtures/*.sample.json`. Edit `scripts/generate-fixtures.ts` and regenerate.
